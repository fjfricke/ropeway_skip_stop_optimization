# MILP Optimization v0

Status: **implemented v0 core**

## Goal

Build the first optimization model on top of the existing `DiscreteScenario`.

The model should initially decide cabin movements on the discrete graph while respecting physical conflict constraints. It should produce a valid `MovementPlan` that can be replayed and visualized with the existing replay and metrics pipeline.

v0 is deliberately a feasibility-first model. Passenger assignment and passenger waiting-time optimization are not part of the first implementation.

## Target Formulation

For v0, the optimizer should solve:

```text
find a collision-free movement plan for all active cabins over the discrete horizon
```

Subject to:

```text
each active cabin occupies exactly one discrete node per time step
```

```text
each active cabin follows exactly one valid outgoing arc per time step
```

```text
arc choices define the cabin position in the next time step
```

```text
all discrete conflict constraints are respected
```

```text
initial cabin positions are respected
```

The first objective can be neutral:

```text
minimize 0
```

After feasibility works, the next main objective is passenger queuing time:

```text
minimize total queuing time
```

## Scope Decisions

### Cabin Activation

The modeling architecture should eventually support multiple activation modes:

- fixed cabins at fixed start nodes
- cabins released from depot/storage stations
- cabins already somewhere in the graph at a given initial time
- optional cabin activation/deactivation decisions

Implemented first:

```text
fixed cabins with fixed start nodes at t = 0
```

The fixed start states can initially come from the existing simple circulation baseline.

### Allowed Arcs

The optimizer should use the directed discrete graph as generated by the discretizer.

Allowed in v0:

- all forward `MOVE` arcs
- all `WAIT` arcs
- all skip/service alternatives already present in the discrete graph

Not allowed:

- reverse movement against the directed graph
- graph edits inside the optimizer

Skip decisions are therefore not a separate primitive in v0. A cabin skips a station when it chooses the skip path arcs at the corresponding switch.

### Objective

The first model is a pure feasibility model:

```text
minimize 0
```

This is intentional. v0 should answer whether the current discrete graph, initial cabin placement, wait arcs, and conflict constraints admit any collision-free movement plan over the requested horizon.

Later objective variants can discourage unnecessary waiting, encourage circulation, or optimize passenger metrics.

### Hard Constraints

Hard in v0:

- one active cabin position per time step
- valid arc continuity between consecutive time steps
- fixed initial cabin positions
- all existing `DiscreteConflict` constraints
- route legality implied by the directed discrete arcs

Not part of v0:

- passenger boarding/alighting decisions
- demand assignment
- passenger waiting-time objective
- boarding capacity
- cabin creation/deletion
- graph rewriting for solver performance

## Modeling Choice

v0 uses a deliberately explicit time-expanded formulation with both position and movement variables:

```text
x[c,t,v] = 1 if cabin c occupies discrete node v at time step t
y[c,t,a] = 1 if cabin c uses discrete arc a from time step t to t+1
```

This is not the most compact possible formulation, but it is the clearest first model for this project:

- conflicts are naturally node-based and can use `x`
- movement continuity is naturally arc-based and can use `y`
- skip/service/wait choices are explicit through chosen arcs
- solver output can be converted back to `MovementPlan` without inference-heavy logic
- debugging against the frontend discrete graph is straightforward

Performance-oriented formulations are intentionally deferred until the model is correct and inspectable.

## Sets And Indices

```text
C = active cabins
T_node = {0, ..., H}
T_arc = {0, ..., H-1}
V = discrete nodes
A = directed discrete arcs
K = discrete conflict constraints
```

Derived incidence sets:

```text
A_out(v) = {a in A | from_node_id(a) = v}
A_in(v) = {a in A | to_node_id(a) = v}
V(k) = nodes covered by conflict constraint k
```

For v0, `C` comes from fixed initial cabin states. `H`, `V`, `A`, and `K` come from `DiscreteScenario`.

v0 does not require a `networkx` graph. The MILP needs direct incidence lookups, not graph algorithms.

Recommended internal index:

```python
@dataclass(frozen=True)
class DiscreteGraphIndex:
    nodes_by_id: dict[str, DiscreteNode]
    arcs_by_id: dict[str, DiscreteArc]
    out_arc_ids_by_node_id: dict[str, tuple[str, ...]]
    in_arc_ids_by_node_id: dict[str, tuple[str, ...]]
    arc_ids_by_endpoints: dict[tuple[str, str], tuple[str, ...]]
```

NetworkX can be added later if we need path search, reachability analysis, connected components, shortest paths, or graph preprocessing. It is intentionally not part of the first MILP implementation.

## Decision Variables

Position variables:

```text
x[c,t,v] in {0,1}
for c in C, t in T_node, v in V
```

Movement variables:

```text
y[c,t,a] in {0,1}
for c in C, t in T_arc, a in A
```

Naive v0 may create these as full cartesian products. Later implementations should restrict variables to reachable `(c,t,v)` and `(c,t,a)` combinations.

## Core Constraints

### Position Assignment

Each active cabin occupies exactly one node at each time step:

```text
sum_{v in V} x[c,t,v] = 1
for c in C, t in T_node
```

### Outgoing Arc Link

If a cabin is at node `v` at time `t`, it must choose exactly one outgoing arc from `v`:

```text
sum_{a in A_out(v)} y[c,t,a] = x[c,t,v]
for c in C, t in T_arc, v in V
```

If `A_out(v)` is empty and `x[c,t,v] = 1` for `t < H`, the model becomes infeasible. This is acceptable in v0 and should be reported clearly.

### Incoming Arc Link

The chosen arc defines the cabin position at the next time step:

```text
sum_{a in A_in(v)} y[c,t,a] = x[c,t+1,v]
for c in C, t in T_arc, v in V
```

### Initial Positions

Fixed cabin starts:

```text
x[c,0,start_node(c)] = 1
for c in C
```

Because position assignment already forces exactly one node, this is enough to exclude all other start nodes.

### Conflict Constraints

Every existing `DiscreteConflict` is enforced as a hard capacity constraint:

```text
sum_{c in C} sum_{v in V(k)} x[c,t,v] <= capacity(k)
for k in K, t in T_node
```

The constraint kind should be preserved in generated solver constraint names or metadata so later relaxed models can selectively inspect or relax groups such as own-headway, adjacent-headway, cross-headway, or multi-headway constraints.

## Objective Roadmap

### v0: Feasibility

```text
minimize 0
```

v0 does not attempt to prefer less waiting, more circulation, more service, or better passenger outcomes. It only proves that the discrete graph, initial states, wait arcs, and conflict constraints admit a collision-free movement plan.

### v1: Total Queuing Time

The first passenger-aware optimization objective should be:

```text
minimize total queuing time
```

Preferred unit for reporting:

```text
passenger-hours
```

Conceptually:

```text
total queuing time = sum over time steps of waiting_passengers[t] * delta_seconds / 3600
```

This is the same operational metric currently exported by replay metrics as:

```text
cumulative_waiting_passenger_hours
```

Important: v1 cannot be implemented as a pure movement-only objective. It requires passenger queue state, boarding decisions, cabin load state, destination compatibility, and alighting events to be represented inside the optimization model or in a coupled optimization/replay scheme.

The v1 objective should count passengers while they are waiting in station queues, including passengers still waiting at the end of the horizon.

### Later Objective Variants

Potential later objectives or tie-breakers:

- minimize cabin waiting arcs
- maximize useful circulation or completed cycles
- maximize served passengers before minimizing queuing time
- penalize excessive station skipping
- enforce service fairness across stations or OD pairs
- balance passenger queuing time against operating cost or energy proxies

## Solver Output

The optimizer output should be converted back into the existing movement model, not into a solver-specific structure.

From position variables:

```text
positions[c][t] = v where x[c,t,v] = 1
```

From movement variables:

```text
arcs[c][t] = a where y[c,t,a] = 1
```

The primary exported object should be:

```python
MovementPlan(
    discrete_scenario_id=discrete_scenario.id,
    horizon_steps=H,
    trajectories=(...)
)
```

Each trajectory should contain the selected node position for every time step:

```text
len(trajectory.positions) = H + 1
```

Arc selections are useful for debugging and objective accounting. If the existing `MovementPlan` model does not store arcs directly, arcs can be reconstructed from consecutive position pairs as long as each transition is unique. If multiple arcs connect the same `(from_node, to_node)`, the solver wrapper should keep a sidecar debug result with chosen arc ids.

The first implementation should return both:

- `MovementPlan` for replay/frontend compatibility
- solver metadata for debugging, including status, objective value, selected arc ids, and constraint counts

## Post-Solve Validation

Every generated movement plan should be validated in Python after solving, even if the solver reports a feasible or optimal result.

Required checks:

- plan references the same `discrete_scenario_id`
- plan horizon equals the solved horizon
- every active cabin has exactly `H + 1` positions
- every referenced node id exists in the `DiscreteScenario`
- every consecutive position pair is connected by at least one allowed directed arc
- fixed initial cabin positions are respected
- every existing `DiscreteConflict` capacity is respected at every time step
- no reverse movement appears unless it exists as a directed arc in the discrete graph

Recommended debug checks:

- selected `y` arcs agree with the reconstructed position transitions
- all selected arcs are part of the allowed arc policy
- conflict violations are reported with conflict id, kind, time step, involved cabins, involved nodes, and capacity
- dead-end infeasibility is reported with node id and time step when possible

This validation should not be Gurobi-specific. It should be reusable for:

- MILP solutions
- greedy baselines
- future heuristics
- imported or manually edited movement plans

## Route And Skip Semantics

v0 has no explicit route variables.

The optimizer only chooses directed discrete arcs:

```text
y[c,t,a] = 1
```

All route, service, skip, and wait behavior is induced by those arc choices.

At a switch node, the graph may expose multiple outgoing alternatives. For example:

```text
entry switch -> service path
entry switch -> skip path
```

The model chooses exactly one outgoing arc through the existing outgoing-arc link:

```text
sum_{a in A_out(v)} y[c,t,a] = x[c,t,v]
```

Therefore:

- a cabin services a station when it follows the service path arcs
- a cabin skips a station when it follows the skip path arcs
- a cabin waits when it follows a wait arc
- a cabin can only move in directions represented by directed arcs

No separate variables are needed in v0:

```text
skip[c,t,station]
service[c,t,station]
route[c,t]
```

These would be redundant for feasibility. They may become useful later for objective terms, reporting, or passenger-service constraints.

The directed graph defines physical legality. Flow constraints define continuity. Conflict constraints define safety.

Operational service quality is intentionally deferred. v0 may find a physically feasible plan that is not useful for passengers, for example a plan where cabins skip too many stations. That is acceptable for the first feasibility model.

After solving, route semantics can be derived from selected arcs:

- skipped station events
- serviced station events
- wait events
- selected switch alternatives
- arc-kind counts per cabin

This derived information belongs in solver metadata or a debug export, not in the core v0 MILP formulation.

## Implementation Structure

Add a new package:

```text
src/ropeway_skip_stop_optimization/optimization/
```

Suggested files:

```text
optimization/
  __init__.py
  graph_index.py
  models.py
  movement_plan_validation.py
  milp_v0.py
```

### `graph_index.py`

Builds deterministic lookup structures from `DiscreteScenario`:

```python
build_discrete_graph_index(discrete_scenario: DiscreteScenario) -> DiscreteGraphIndex
```

Responsibilities:

- node lookup by id
- arc lookup by id
- outgoing arc ids by node id
- incoming arc ids by node id
- arc ids by `(from_node_id, to_node_id)`
- optional validation for duplicate ids and dangling arc endpoints

### `models.py`

Optimization-specific dataclasses that are not tied to Gurobi:

```python
@dataclass(frozen=True)
class FixedCabinStart:
    cabin_id: int
    node_id: str


@dataclass(frozen=True)
class MilpV0Config:
    horizon_steps: int
    fixed_starts: tuple[FixedCabinStart, ...]
    allow_move_arcs: bool = True
    allow_wait_arcs: bool = True
    allow_skip_arcs: bool = True


@dataclass(frozen=True)
class MilpSolveMetadata:
    status: str
    objective_value: float | None
    selected_arc_ids_by_cabin: dict[int, tuple[str, ...]]
    variable_count: int
    constraint_count: int


@dataclass(frozen=True)
class MilpMovementPlanResult:
    movement_plan: MovementPlan | None
    metadata: MilpSolveMetadata
```

The config should eventually support depot release and non-fixed starts, but those modes are not implemented in v0.

### `movement_plan_validation.py`

Reusable validation for movement plans:

```python
validate_optimized_movement_plan(
    discrete_scenario: DiscreteScenario,
    movement_plan: MovementPlan,
    fixed_starts: tuple[FixedCabinStart, ...] = (),
    selected_arc_ids_by_cabin: Mapping[int, tuple[str, ...]] | None = None,
) -> MovementPlanValidationResult
```

This validator should be independent of Gurobi and reusable for:

- MILP output
- greedy baselines
- future heuristics
- imported plans

### `milp_v0.py`

Gurobi-specific v0 model builder and solver:

```python
solve_milp_v0(
    discrete_scenario: DiscreteScenario,
    config: MilpV0Config,
) -> MilpMovementPlanResult
```

Responsibilities:

- build `x[c,t,v]` and `y[c,t,a]`
- add position, flow, initial-state, and conflict constraints
- set objective `minimize 0`
- solve
- extract selected positions and arcs
- build `MovementPlan`
- run post-solve movement-plan validation
- return solver metadata

`gurobipy` should be imported inside `solve_milp_v0`, not at package import time, so the rest of the project remains usable without a Gurobi installation.

If `gurobipy` is unavailable, the solver should fail with a clear runtime error:

```text
gurobipy is required for MILP optimization
```

## Implementation Order

Implemented:

- optimization dataclasses
- `DiscreteGraphIndex` and tests
- reusable movement-plan validator and tests against the existing greedy baseline
- negative validator tests for bad transitions, bad initial states, node occupancy, and conflict violations
- `solve_milp_v0` with lazy `gurobipy` import
- optional Gurobi test for a very short horizon, skipped when `gurobipy` is unavailable
- MILP output conversion to `MovementPlan`

Not implemented yet:

- CLI/export entry point for solved MILP plans
- frontend visualization of solved MILP plans as distinct artifacts
- passenger-aware v1 queuing-time optimization
- depot release or non-fixed cabin activation modes
